Windows DVB-T2 investigation, 2026-11-08
======================================

Update 2026-11-09: comparison hardware is DIFFERENT
-------------------------------------------------
User read Windows Task Manager: AMD Ryzen 5 5500H. AMD specifies 4 cores /
8 threads. Local Linux lscpu and decoder runtime report Ryzen 7 5800H,
8 cores / 16 threads. Thus the earlier assumption of equal-spec hardware is
incorrect. Historical Linux/Windows reception and per-call CPU timings do
not isolate the operating system. This is a substantial capacity difference,
not proof that hardware alone explains all loss. No claim of exactly twice
the performance follows from twice the core count.
Sources: build/t2-bench/receiver-cpu-comparison-20261109.json and
https://www.amd.com/en/support/downloads/drivers.html/processors/ryzen/ryzen-5000-series/amd-ryzen-5-5500h.html

Outcome
-------
A reproducible receiver defect BEFORE LDPC was found and fixed. Known input
sample gaps reset resampler state, but the next P1 detection was compared with
a synthetic pre-gap position as though both positions were continuous clock
measurements. Repeated short gaps integrated a false sample-clock correction
(SRO), eventually damaging P2/L1 and preventing recovery after the gaps stopped.
The fix preserves predicted P1 cadence for acquisition, but requires two real
P1 detections without an intervening gap before measuring frame spacing again.

This establishes a failure mechanism after sample loss. It does NOT establish
the initial reason why the Windows input queue fills, nor prove that every
live Windows failure has this cause. Native Windows live validation of this
change remains pending. Missing samples themselves cannot be recovered.

The GUI Service Info Buffer is the worker INPUT queue occupancy, not RF signal
strength or LDPC queue occupancy (src/dvbt2_backend.cc). Capacity is 64 blocks
of 65,536 samples, about 419 ms at 10 MS/s. It can rise during a processing
burst and drain afterwards. A 100% snapshot alone is not a loss measurement;
increasing input_dropped proves discarded input. Stronger/usable reception
also enables work that is absent while searching, but this is not evidence
that signal amplitude directly causes overflow. The pipelined resampler has
its own bounded queue. SDR hardware overflow, SDR writer drops, decoder input
drops and FEC frame drops must be kept separate.

Our additional audit
--------------------
Windows stdin/stdout/stderr and pipes are explicitly binary in
src/win32/platform.c. The DVB-T2 adapter accumulates short reads, preserves
four-byte sc16 sample boundaries and normalizes signed int16 values. Slowed
recorded-IQ replays under Wine produce byte-identical TS to Linux. These checks
argue against generic newline conversion/short-read corruption, but do not
prove native Windows UHD sample continuity or exclude an upstream defect.

components/dvbt2/src/t2/t2rx_l1.cpp can reuse cached L1 for up to eight frames,
including dynamic PLP placement/block counts. L1 counters can record a CRC
failure while processing continues with reused information. The endpoint
does not currently distinguish fresh versus reused L1 in its boolean status.
This remains a possible amplifier of damage, not a proven initial cause.

The retry policy can spend up to three additional 150-iteration attempts
under its backlog/time checks. Those checks do not see the host input queue.
Thus high retry CPU can contribute to feedback after corruption, but the
no-LDPC regression proves that clock recovery itself can fail first.

Why Linux can still work well
----------------------------
The defect is shared portable code, not a Windows-only arithmetic defect.
It is triggered by sample gaps and their timing. Saved Linux runs had either
zero loss or about 0.31%, versus 7-12% in affected Windows runs. Those different
conditions can expose the same bug much more strongly on Windows. This is a
supported mechanism, not proof of why Windows initially has less headroom.
Native CPU scheduling, actual EcoQoS, driver/USB behavior and processing bursts
still require a matched live profile. Keep hardware, antenna, gain, sample
rate and PLP identical; do not compare dissimilar historical runs as controlled
experiments. Do not run heavy benchmarks beside a live receiver.

Follow-up: isolate Windows EcoQoS (user-authorized change)
-------------------------------------------------------
The Windows FEC background thread policy now explicitly requests execution-
speed throttling OFF (ControlMask=1, StateMask=0). Scheduling priorities, worker
counts, queues and decoder algorithms are unchanged. Each affected thread logs
API acceptance, failure with GetLastError, or absence of SetThreadInformation.
Acceptance is not proof of higher frequency or improved live throughput.
The default background pool count is the same on both OSes: max(1, min(8,
hardware_concurrency - 1)), plus the participating PLP thread. This does not
bind those workers to particular cores. Linux has additional heterogeneous
core affinity rules for non-background work; Windows placement is OS-managed.
Native Windows A/B reception remains needed with the same settings/player.

Follow-up: CPU versus wall-time instrumentation (2026-11-09)
----------------------------------------------------------
The profile now measures exclusive elapsed wall time as well as thread CPU
time. New stages cover host input waits, conversion, receiver feeding/polling,
reporting, TS delivery/flush, resampler capacity waits and parallel worker
completion waits. Parallel wall times overlap: their sum is not process
elapsed time. Difference from CPU includes blocking and scheduling delays.
Startup reports logical processor count and requested worker count; HTTP
decoder telemetry exposes buffer_valid and buffer_percent. This changes
diagnostics, not decoder algorithms, queue capacities or thread policies.

Tests: nested sleeping stage records wall time without double counting or

A separate Linux replay deliberately stalls the TS reader for 350 ms: TS

Follow-up: LDPC value-based minima (2026-11-09)
---------------------------------------------
The user requested prioritising LDPC. In the last GPU-renderer-confirmed
89.356 s Windows interval, main LDPC accounted for 234.109 CPU seconds summed
over its parallel workers; retries added only 4.641 s. Thus the main LDPC
kernels, rather than retry limits alone, remain a useful CPU target.

Both x86 AVX2 kernels (independent-group blocked layers and repeated-group
buffered layers) now track only the two smallest magnitudes and the sign
product. They no longer track which connection provided the minimum.
Updating m2 as min(m2, max(m1, a)) before updating m1 preserves the second
minimum. At message generation, an input whose magnitude equals m1 uses m2.
If multiple inputs tie, m2 equals m1, so this gives the original magnitude
for all tied connections. Sign calculation, floating-point subtraction and
addition order, layer order, alpha, iteration limits and retry policy remain
unchanged. This identity targets finite LLR values. Generic and NEON paths
are unchanged. Runtime log: DVB-T2 LDPC: avx2 value-minima.

Short alternating tests on the Linux Ryzen 7 5800H at normal 3/5 (64800 bits)

Follow-up: channel-stage decomposition and memory traffic (2026-11-09)
--------------------------------------------------------------------
The user authorised splitting and optimising channel estimation/equalisation.
Detailed t2.ce.* and t2.eq.* stages show that the old t2.eqloop includes PLP
assembly, buffer preparation and interference tracking, not just division by
channel coefficients. In a slowed existing recording under Wine, preparing
and submitting the PLP cost 0.397 s of a 1.097 s total over 11 frames. The
actual equalisation arithmetic and channel interpolation were much smaller.

Three changes preserve the signal processing arithmetic:
- Remove pilot observations gathered before phase correction: they were
  cleared without being read, then rebuilt from the corrected cells.
- Keep data-cell/noise vectors with the frontend and resize once per frame.
  Every position is overwritten through the existing interleaver permutation;
  erased symbols explicitly write zeros/large noise. PLP jobs own their copy.
- Copy the selected PLP range directly from gathered P2 and data symbols,
  avoiding full concatenated intermediate cell/noise vectors. Bounds checks
  reject invalid ranges before touching output. P2 noise arithmetic is identical.

Both instrumented builds process the same existing recording at quarter speed.
Linux full channel-stage CPU falls 0.635 -> 0.455 s (sync) and 0.679 -> 0.475 s
(pipelined). Windows-under-Wine elapsed stage time falls 1.095 -> 0.824 s and
1.097 -> 0.825 s, about 25%. These totals sum parent plus exclusive children,
cover 11 profiled frames, and are NOT native Windows 5500H measurements or
whole-receiver throughput. Startup marker:
DVB-T2 channel processing: direct PLP assembly, reusable buffers

42,318 PLP ranges match the original concatenation/slice method byte-for-byte,
